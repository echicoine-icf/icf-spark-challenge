# SPARK Milestone 5D — Typed biomedical concept normalization

## Purpose / safety contract

**This is the typed normalization and guarded query-expansion layer, not dbGaP study enrichment.** The original challenge corpus remains unchanged. It answers: *Does the exact term occur as a canonical label or EXACT synonym of one unique concept in an active, versioned biomedical terminology?* If so it can attach a concept ID and use a small number of **that concept's** original EXACT synonyms in original-metadata search. A SapBERT cosine neighbor is only a suggested candidate for review. It never authorizes synonym expansion or fact generation.

The implementation deliberately distinguishes:

| Requested type | Source / rule | Current status |
|---|---|---|
| `disease` | Active MONDO concept; source provenance pinned | Supported |
| `phenotype` | Active HPO/HP concept with an `is_a` ancestry path to `HP:0000118` (phenotypic abnormality) | Code ready; requires separately imported HPO ontology and, for semantic hints, HPO vectors |
| `medication` | RxNorm (planned) | **Not integrated**; no MONDO approximation |
| `laboratory_measurement` | LOINC (planned) | **Not integrated**; no MONDO approximation |
| `auto` | Search active MONDO and HPO exact labels/synonyms; accept only if one unique, validated, typed concept | Supported, fail-closed if ambiguous |

**Caveat:** MONDO's domain categorization is source-level typing; it does not establish that a clinical measurement, therapy or phenotype is captured in dbGaP. HPO contains non-phenotypic categories; an HPO namespace alone does not authorize phenotype typing. HPO relationships are read only for bounded type-ancestry validation; parents, siblings, xrefs and RELATED synonyms are never used as equivalent query expansions.

## Endpoints

- `GET /api/v1/ontology/normalize?term=T2DM&expected_type=disease` — exact normalization, approved synonym expansions, release/checksum and provenance, optional semantic suggestions **only when no exact match**.
- `GET /api/v1/ontology/normalize?term=diabetes%20type%202&expected_type=disease` — non-exact spelling; SapBERT offers candidate matches for review, `normalized_concept=null`, `expansions=[]`.
- `GET /api/v1/ontology/normalize?term=blood%20glucose&expected_type=laboratory_measurement` — `terminology_not_integrated`, never maps a measurement to diabetes or hypoglycemia.
- `GET /api/v1/ontology/normalize?term=renal%20function&expected_type=laboratory_measurement` — no disease reinterpretation.
- `GET /api/v1/search/normalized?q=T2DM&expected_type=disease&limit=5` — uses verified EXACT synonyms and the original source search; semantic suggestions never enter retrieval. The separate `/api/v1/search/ontology` endpoint remains unchanged.

Optional params: `ontology=MONDO|HP`, `include_semantic=false` (deterministic without inference service), `max_expansions=0..8`, `candidate_limit=1..20`. For a disputed or context-sensitive query, pass `expected_type` rather than using `auto`.

**Statuses:** `normalized_exact`, `ambiguous_exact`, `unclassified_exact`, `type_mismatch`, `ontology_type_mismatch`, `terminology_not_integrated`, `terminology_not_loaded`, `not_found`. `semantic_status` independently reports `not_needed_exact_evidence`, `disabled`, `model_unavailable`, `candidates_for_review`, or `no_indexed_candidates`, or `not_available`.

The new search endpoint uses the existing lexical ranker and preserves `direct_original_match` / `query_expansion_only`. Neither label means a record was generated by AI or that participant-level evidence exists. A score is **not** a confidence/probability of clinical equivalence.

## Install / run in Windows Git Bash

Extract the Milestone 5D ZIP to the repo. No migrations, reimports, reindex, Docker volume changes or ontology downloads are needed. Your existing MONDO release (32,137 concepts / 92,235 terms), SapBERT service and full HNSW index are reused.

```bash
cd /c/ESAC_DEV/DEVELOPMENT/SPARK/icf-spark-challenge
docker compose up -d --build api
python sparkctl.py normalization-smoke

curl 'http://localhost:18080/api/v1/ontology/normalize?term=T2DM&expected_type=disease'
curl 'http://localhost:18080/api/v1/ontology/normalize?term=diabetes%20type%202&expected_type=disease'
curl 'http://localhost:18080/api/v1/ontology/normalize?term=blood%20glucose&expected_type=laboratory_measurement'
curl 'http://localhost:18080/api/v1/search/normalized?q=T2DM&expected_type=disease&limit=5'
```

For timing, review status, and candidate safety comparisons:

```bash
docker compose --profile tools run --rm --build ontology-normalization-benchmark
```

Results: `reports/normalization_baseline.json`. The benchmark is **not a NDCG or clinical-validity test**. If SapBERT is stopped, exact matching and lexical search still work; unresolved queries show `semantic_status=model_unavailable`.

The unified `sparkctl bootstrap` rebuilds the API and preserves its existing non-destructive deployment workflow. No `sparkctl lock-assets` refresh is required for this code-only patch; the model and ontology checksums are unchanged. Repackage the frozen source alongside your model/data lock when preparing NIH artifacts.

## Engineering tests and remaining gates

- Unit tests cover exact-synonym acceptance, ambiguity and truncation, MONDO/HPO typing, unsupported source types, model outage fallback, and absence of semantic suggestion terms in retrieval.
- HPO ancestry classification must be validated against a real versioned HPO import; not currently available locally.
- Real end-to-end testing of the new endpoints against the developer PostgreSQL and CUDA SapBERT service is required after applying the patch.
- A contextual biomedical entity recognition step is still missing; `expected_type=auto` cannot infer intent such as "blood glucose measurement" vs a diagnosis reliably. The future query parser/Qwen must emit explicit typed slots with evidence, and unsafe / ambiguous results should require clarification or lexical fallback.
- Appropriate licensed/pinned LOINC, RxNorm (and possibly SNOMED CT/UMLS) adapters are the next terminology prerequisites. No external study-specific data, participant-level records or uncontrolled internet retrieval should be used.


### Live acceptance and benchmark readiness

Validated in the developer environment: canonical `type 2 diabetes mellitus` and `T2DM` normalize as exact; unsupported medication and laboratory measurement types fail closed; non-exact paraphrases remain semantic suggestions only. Two-trial benchmark medians were 13.1–40.0 ms without semantic inference and 779.6–972.6 ms when SapBERT was invoked. First benchmark invocation hit an API recreation/startup race; the explicit `--no-deps` rerun after `/ready` passed. A follow-up patch makes API startup gating automatic with a Compose healthcheck and bounded in-benchmark retry. This is not an NDCG or relevance judgment.

## Milestone 5E: LOINC/RxNorm (optional pinned source ZIPs)

The prior 5D status `terminology_not_integrated` for medication and laboratory measurement is superseded after deploying 5E code: if a source is not yet imported, its type lookup returns `terminology_not_loaded`. Once a release is active, unique exact matches may return `normalized_exact` for medications (RxNorm) and laboratory measurements (LOINC). Other possible outcomes include `not_found`, `ambiguous_exact`, `unclassified_exact`, or `type_mismatch` without automatic expansion. A typed medication request only searches `RXNORM`, and a typed laboratory measurement request only searches `LOINC`.

LOINC long common name and same-code shortname, and active RxNorm same-RXCUI normalized names, are the only additional expansion-capable name fields. No LOINC `RELATEDNAMES2`, RxNorm cross-RXCUI substitutions, or unverified SapBERT neighbors are promoted. Missing LOINC/RxNorm vectors are explicitly identified as `no_semantic_index_for_source`, not silently delegated to disease terms in MONDO. Source preparation, restrictions and commands: [`TERMINOLOGY_INTEGRATION.md`](TERMINOLOGY_INTEGRATION.md).
